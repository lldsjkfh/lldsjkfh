# Sherman：面向内存解耦架构的写优化 B+ 树索引（SIGMOD 2022）

> 一句话：把内存从 CPU 板子上拆走之后，B+ 树的「写」被打回原形——不改架构、不换硬件，靠三处协同设计把写吞吐拉回一个数量级。

## 一句话总结

内存解耦把「计算」和「容量」拆到两台机器上，索引的每次写都要跨 RDMA 往返；Sherman 没有改架构也没有换硬件，而是用 RDMA 的**保序语义**、**网卡片上内存**和**两级版本**三处协同设计，把写路径的往返、锁竞争和写放大同时压下去。

## 核心贡献

1. **命令合并（command coalescing）**：利用 RC 连接的按序交付特性，把「写回」与「解锁」合并成一次投递——94% 的写从 4 次往返降到 3 次。
2. **分层片上锁 HOCL（Hierarchical On-Chip Lock）**：把全局锁表放进 RDMA 网卡的片上内存，本机再加一层锁表，把「一次原子操作两次 PCIe 事务 + 按地址分 4096 桶串行」的远程锁开销拆掉。
3. **无序叶子 + 两级版本**：叶子节点不再维持有序，插入落到空位、不做元素搬移，只回写 17 B（原来要整节点 1 KB）；用两级版本号解决无序带来的读一致性。
4. **结论的诚实边界**：收益高度集中在**倾斜写**（24.7×），均匀负载只有 1.15×——这是全篇最该记住的一句。

## 方法要点

### 问题从哪来

内存解耦架构里，**所有 CPU 都在 CS（compute side）一侧，MS（memory side）只剩 DRAM 和一块网卡**——MS 侧几乎没有算力，语义只有 RDMA 的 read/write/CAS/fetch-add。于是 B+ 树的每次写都变成一次跨网络的状态机：

```
取锁 → 读 → 改 → 写回 → 解锁
```

三个痛点层层递进：

| 痛点 | 具体表现 |
| --- | --- |
| Ⅰ 网络往返过多 | 94% 的写需要 4 次往返；抢锁时 p99 达到 453 次往返 |
| Ⅱ 远程锁同步慢 | 一次原子操作要两次 PCIe 事务；网卡按地址哈希分 4096 个桶，同桶请求串行 |
| Ⅲ 写放大严重 | 改一个条目，也要把整个 1 KB 节点写回 |

问题收敛成一句：**不改架构、不换硬件，怎么让单边 RDMA 的写变快。**

### 三个技术分别打哪个痛点

**① 命令合并 → 打「往返次数」。**
「写回」和「解锁」本来是两条独立命令，但它们的顺序是确定的。RC 连接保证同一 QP 上的请求按序交付，所以可以把两条命令一次投递，省掉一次等待。这一步不是靠新硬件，而是靠「把协议的保证用起来」。

**② HOCL → 打「远程锁」。**
把全局锁表搬进网卡片上内存（on-chip memory），锁操作不再落到 MS 的 DRAM；再在 CS 本地加一层锁表，让大部分竞争在本地就被吸收。论文报告 3.06×，叠上本地锁后到 3.85×。

**③ 无序叶子 + 两级版本 → 打「写放大」。**
有序叶子插入要搬移元素，一搬就得整节点写回。改成无序后，插入直接落到空位，只写 17 B。无序的代价是范围查询要额外排序，同时读需要版本号来保证不读到「写了一半」的节点——这就是两级版本的作用。代价：约 +6% 空间，范围查询略降（论文承认低约 2%）。

## 实验结论

对比基线 FG+（同样面向解耦内存的 B+ 树）：

| 负载（对 FG+） | 吞吐 | p99 延迟 |
| --- | --- | --- |
| 写仅 · 倾斜 | **24.7×** | 低 **35.8×** |
| 写密集 · 倾斜 | **23.6×** | 低 **30.2×** |
| 写仅 · 均匀 | 1.24× | 低 2.01× |
| 写密集 · 均匀 | 1.15× | 低 1.27× |

单项贡献：命令合并 3.37×、锁放片上 3.06×、再叠本地锁 2.22×。

**边界（论文自己承认的）**：模拟环境而非真机集群；依赖 ConnectX-5 的网卡特性（片上内存、保序）；range 查询比 FG+ 低约 2%。

## 我的思考

1. **「性能问题要拆到硬件层次去归因」是这篇最值得学的地方。** 它没有停在「RDMA 写太慢」，而是继续往下问：慢在往返次数（协议层）、慢在 PCIe 事务与网卡分桶（硬件层）、慢在整节点写回（数据结构层）。三层各有各的药——命令合并、HOCL、无序叶子。这种「先归因到层，再对症下药」的拆法，比记住三个技术名词更有用。
2. **收益的分布比收益的大小更重要。** 24.7× 和 1.15× 是同一个系统在两种负载下的表现。如果只看标题数字，很容易以为它「全面快一个数量级」；实际上它优化的是**冲突**，没有冲突时它几乎没有优势。看论文的实验表要专门找「最差的那一行」。
3. **无序是一种「用查询换写入」的交易。** 无序叶子把写放大从 1 KB 压到 17 B，代价转移到了范围查询和版本校验上。这和我做时序预测时遇到的 Instance Norm 取舍是同一类问题：**没有免费的优化，只有把代价挪到另一个地方**——关键是挪到你不敏感的那一侧。
4. **可迁移的一点**：Sherman 的「把数据结构布局对齐到硬件的访问粒度」这个思路，在做任何存储/索引相关的工作时都成立。写 17 B 而不是 1 KB，本质上是让写的粒度等于实际变化的粒度。
