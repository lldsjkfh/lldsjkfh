# 三种锁的实测对比：mutex / 自旋锁 / 原子自旋

> 要回答的问题：**「自旋锁一定比 mutex 快吗？」** 结论是不一定——临界区长度和线程数会各改一次答案，超过核数之后自旋会崩。

## 一、三把锁的差别

| 锁 | 无竞争时 | 有竞争时 | 适合 |
| --- | --- | --- | --- |
| `pthread_mutex_t` | 一次 CAS 快路径 | **把线程挂起睡眠**，让出 CPU | 临界区较长、竞争不可预测 |
| `pthread_spinlock_t` | 一次原子操作 | **原地空转**等，不让出 CPU | 临界区极短（几十 ns）、持有时间确定 |
| 原子自旋（`atomic_flag` + acquire/release） | 一条原子指令 | 同上，但比库函数更轻（无函数调用、无内嵌记账） | 同上，且能接受自己处理内存序 |

三者的共同点：**都保证互斥与可见性**。差别全在「抢不到的时候干什么」——睡眠还是空转。

## 二、实验设计

五个控制项：

| 变量 | 取值 |
| --- | --- |
| 锁类型 | mutex / spinlock / 原子自旋 |
| 线程数 | 1 / 6 / 12 / 24 / 48（本机 12 核，所以有「核内」与「超核」两段） |
| 临界区长度 | 极短（几条指令）/ 微秒级 |
| 循环次数 | 固定总工作量，换算成 Mops / Kops |
| 环境 | 本机 12 核、Windows/MinGW 复跑，**未绑核** |

之所以线程档取 1/6/12/24/48，是为了让 **12（= 核数）** 成为一个分界点：往上就进入超核，能直接看出「空转」这件事什么时候开始亏。

## 三、结果

### 短临界区（极短，几条指令）

| 场景 | mutex | 原子自旋 |
| --- | --- | --- |
| 单线程 | 176 Mops | **345 Mops**（≈1.96×） |
| 48 线程 | **34 Mops（0.20×）** | 5 Mops（**0.01×**） |

- 单线程时原子自旋几乎快一倍：省掉了进入内核、维护等待队列这些固定开销。
- 到 48 线程直接反转：mutex 还剩 0.20×，原子自旋掉到 0.01×——**掉了两个数量级**。

### 长临界区（微秒级）

| 场景 | 表现 |
| --- | --- |
| mutex | 261 → 224 Kops，**加速比 ≈ 1** |
| 原子自旋 | 363 → 177 Kops（**0.49×**），空转白烧核 |

长临界区下，吞吐本来就由「临界区本身串行」决定，加线程几乎不涨（mutex 1×）。而自旋反而**减半**：等的那段时间在烧 CPU，还挤压了持锁线程的时间片。

## 四、超核为什么崩

```
核数 = 12，线程 = 48
→ 一定存在「持锁线程被 OS 切走」的时刻
→ 等待者仍在空转，但它占着核不让出来
→ 更多的核被空转吃掉，持锁线程更难拿到时间片
→ 恶性循环，吞吐趋近 0
```

mutex 走的是相反的路：抢不到就**睡**，主动让出核，等被唤醒再抢。所以超核时它虽然也掉（0.20×），但**掉的是线性量级，不是指数**。

## 五、结论

1. **自旋只在「核内 + 临界区极短」赢**。单线程 1.96× 是它的上限，一旦线程数超过核数就迅速转负。
2. **超过核数就别自旋**。这是本周实验最硬的一条：48 线程下 0.01× 不是「慢一点」，是「基本不可用」。
3. **临界区长，用 mutex**。临界区本身串行时，加线程不涨吞吐（≈1×），这时候该优化的是「缩短临界区」，而不是换锁。
4. **原子自旋比 `pthread_spinlock_t` 更轻，但也更容易写错**——内存序（acquire/release）得自己保证，编译器重排和 CPU 重排都要考虑。

## 六、方法论

- **控制变量**：锁类型 × 线程数 × 临界区长度，三个维度分开扫，才能看出「哪个变量在哪一段起作用」。
- **换算成统一单位**（Mops / Kops）而不是看「耗时多少秒」，否则不同配置之间没法比。
- **本组实验的两个短板**：
  1. **未绑核**：线程会漂移，超核那段的数字有噪声，严格结论需要在 Linux 上用 `taskset` 绑核重跑；
  2. **Windows/MinGW 复跑**：`pthread` 在 MinGW 上是另一套实现（winpthreads），与 glibc 的自旋/睡眠策略不同，**绝对值不能直接与 Linux 比，趋势可以**。
