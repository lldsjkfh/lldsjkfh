# Linux：线程同步与线程池

> 上周把「线程怎么建、怎么收」讲完了，这周补上真正难的部分：**多个线程怎么安全地共享状态**，以及把这些零件拼成一个能用的线程池。
> 一条主线：互斥锁保护数据，条件变量/信号量负责「等」，线程池负责「复用」。
>
> 本周的线程池代码见 [threadpool.c](./threadpool.c)（单文件，`make` 即可编译），语义对齐 GLib `g_thread_pool_free(pool, immediate, wait_)`。

## 一、信号量 vs 条件变量：一个数资源，一个等状态

两者都能让线程「等」，但等的东西完全不同：

| | 条件变量 `pthread_cond_t` | 信号量 `sem_t` |
| --- | --- | --- |
| 等什么 | **一个判断条件**（队列非空、任务未完成） | **还有没有额度**（计数 > 0） |
| 是否自带计数 | 否 | 是 |
| 是否必须配锁 | **必须**，条件判断本身要互斥保护 | 不必，`sem_wait`/`sem_post` 本身原子 |
| 典型用途 | 生产者-消费者里「队列空/满」 | 限制并发数、资源池、次序控制 |
| 唤醒语义 | 广播/单播，被唤醒后要**重新检查条件** | 计数减一，减不到就阻塞 |

**为什么条件变量必须配 mutex**：`while (q_empty) cond_wait(&cond, &mutex);` —— 检查条件和进入等待必须是原子的，否则「检查完为空 → 别人放入任务 → 你才开始等」就会永远等下去。`cond_wait` 在挂起前会原子地释放 mutex，被唤醒后再重新持有，所以检查必须放在锁内。

**实战里最容易错的两件事**：

1. **用 `if` 代替 `while` 判条件**。条件变量可能**虚假唤醒**（spurious wakeup），也可能被广播唤醒但条件已被别的线程抢走。用 `if` 只检查一次，就可能读到空队列。**一律写 `while`。**
2. **信号量忘了配对的 `sem_post`**。`sem_wait` 减一、`sem_post` 加一，少一次 post 就直接把后来的线程锁死，而且不报错。

## 二、有名信号量 vs 无名信号量：差别只在「找不找得到」

| | 无名 `sem_init` | 有名 `sem_open` |
| --- | --- | --- |
| 生命周期 | `sem_init` → 用 → `sem_destroy` | `sem_open` → `sem_close` → `sem_unlink` |
| 怎么找到它 | **没有名字，只能靠地址传** | 靠 `/name` 汇合，`/dev/shm` 下有实体文件 |
| 跨进程条件 | `pshared` 必须非零，且 `sem_t` 本身必须落在共享内存里 | 天然跨进程，还能设权限（0644） |
| 适用 | 同进程线程间；或已经在共享内存里 | 无亲缘关系的进程之间 |

两个细节：

- **`pshared=0` 是线程间，非 0 才是进程间**。如果 `pshared` 非零但 `sem_t` 放在普通全局变量里，每个进程操作的是各自的副本——**各进程各管各的，看起来「同步没生效」**。
- **`sem_unlink` 只删名字，不删对象**。已经 `sem_open` 的进程继续可用，等最后一个使用者 `sem_close` 后才真正释放。

选型：同进程或已经在共享内存里，用无名（快、少一次名字解析）；跨陌生进程用有名，代价是要管权限和 `unlink`。

## 三、线程池：实现拆解（对照 `threadpool.c`）

### 数据结构

```c
typedef struct task {
    void (*func)(void *);      // 任务函数
    void *arg;                 // 任务参数
    void (*destroy)(void *);   // 参数析构：执行完 或 被丢弃 都要调
    struct task *next;
} task_t;

struct threadpool {
    pthread_mutex_t lock;
    pthread_cond_t  cond;      // 有任务 或 关闭 时唤醒 worker
    task_t *head, *tail;       // 手写链表队列（FIFO）
    int count;                 // 队列长度（目前只维护、不读）
    pthread_t *threads;
    int nthreads;
    int shutdown;              // 1 = 不再接受新任务
};
```

用**手写链表**而不是数组队列，是为了出队/入队都是 O(1) 且不用搬数据；代价是每个任务一次 `malloc`。

### worker 主循环：三个关键点

```c
for (;;) {
    pthread_mutex_lock(&pool->lock);

    while (pool->head == NULL && !pool->shutdown)   // ① while 防虚假唤醒
        pthread_cond_wait(&pool->cond, &pool->lock);

    if (pool->head == NULL && pool->shutdown) {     // ② 两个条件缺一不可
        pthread_mutex_unlock(&pool->lock);
        break;
    }

    task_t *t = pool->head;                         // ③ 锁内只做出队
    pool->head = t->next;
    if (pool->head == NULL) pool->tail = NULL;
    pool->count--;
    pthread_mutex_unlock(&pool->lock);              // 先解锁

    t->func(t->arg);                                // 再执行（锁外）
    if (t->destroy) t->destroy(t->arg);
    free(t);
}
```

1. **`while` 而不是 `if`**：虚假唤醒后条件可能已经不成立，必须重新检查。
2. **退出条件是「队列空 **且** 已关闭」**：只看「队列空」会让池子一空闲就退出；只看「已关闭」会丢掉队列里剩下的任务。这个组合也正是 `immediate=0` 时「让 worker 处理完存量」的实现方式——不需要额外代码，靠的就是 worker 在 `shutdown` 之后仍然会出队执行。
3. **锁内只出队，执行在锁外**：否则所有 worker 被串成一条线，线程池退化成单线程。

### 创建：失败要能回滚

`pthread_create` 可能在第 3 个线程时失败。此时不能直接 `return NULL`，必须把已建好的线程收回来：

```
置 shutdown → broadcast 唤醒已建的 worker → join 它们 → 逐个 destroy + free 队列任务
→ destroy 锁与条件变量 → free threads / pool
```

少任何一步，要么泄漏，要么留下还在跑的线程访问已释放的池。

### 提交任务

`push` 里做两件事：链表尾部插入（空队列时同时更新 `head`），然后 `pthread_cond_signal` 唤醒**一个** worker（不是 broadcast——只有一个新任务，唤醒全部会造成惊群）。

### 关闭：`immediate` × `wait_` 四种组合

```c
void threadpool_free(threadpool_t *pool, int immediate, int wait_);
```

| | `wait_=1` | `wait_=0` |
| --- | --- | --- |
| `immediate=1` | 丢弃队列 → 等正在跑的做完 → 函数返回 | 丢弃队列 → **立即返回**，detached `cleaner` 后台 join |
| `immediate=0` | **跑完队列** → 等全部结束 → 函数返回（优雅关闭） | 跑完队列，但函数立即返回 |

实现上分三步：**置 `shutdown` +（可选）清空队列 → `broadcast` 唤醒所有 worker → 按 `wait_` 决定同步 join 还是交给 `cleaner`**。

`wait_=0` 那条路要建一个 detached 的 `cleaner` 线程去 join，因为本线程不能阻塞；而 `cleaner` 万一创建失败，必须**退化成同步清理**，否则整块内存就漏了。

**一条硬保证**：无论哪种组合，**正在执行的任务都不会被打断**。`shutdown` 只在「取任务」时检查，取到手的任务一定跑完。

## 四、实测：四种组合跑出来的行为

`make && ./threadpool`，3 个 worker、8 个任务、每个 80 ms，提交后 50 ms 开始关闭：

| 组合 | 观察到的行为 |
| --- | --- |
| `(0, 1)` 安全关闭 | 8 个任务全部执行完才返回 |
| `(1, 1)` 丢弃 + 等 | 队列里 5 个立刻 `discarded`，正在跑的 3 个跑完才返回 |
| `(0, 0)` 保留 + 立即返回 | 函数立刻返回，但**剩下的任务随进程退出丢了** |
| `(1, 0)` 丢弃 + 立即返回 | 队列清空，正在跑的不受影响，函数立刻返回 |

两个从输出里看出来的点：

1. **`destroy` 是「参数析构」，不是「丢弃专用」**。日志里成功执行的任务也会打印 `discarded`，因为 worker 跑完任务同样会调 `destroy(arg)`。命名容易误导，读代码时要按「谁负责释放 `arg`」来理解它。
2. **`wait_=0` 的语义边界：函数返回 ≠ 任务完成**。`(0,0)` 那一组，`threadpool_free` 返回后进程马上退出，detached 的 cleaner 和剩下的任务一起被回收掉了。这不是 bug，而是 `wait_=0` 的契约——真要等任务跑完，要么用 `wait_=1`，要么在退出前自己等一个完成信号。**GLib 的 `g_thread_pool_free` 也是同样的语义。**

## 五、已知问题（可以改的三处）

1. **`push` 在池已关闭时直接 `free(t)`，没有调 `t->destroy(arg)`** —— 调用方传进来的 `arg` 就泄漏了。同一个文件里，`threadpool_free` 的丢弃路径是调了 `destroy` 的，两处不一致。
2. **`threadpool_free` 没有防重入**：`pool` 指针既不置空也没有 `freed` 标志，重复调用会 double-free。
3. **`count` 字段只维护、没人读**，也没有动态扩缩容——固定 `nthreads`，任务积压时不会扩容、空闲时不会回收。

这三条正好对应下周要做的「线程池动态扩缩容 + 超时任务」。
